# 拾光客服的产品设计与面试讲解

本项目围绕一个问题展开：用户以自然语言分轮提供信息时，客服能否保留当前任务，完成有依据、可确认、可检查的服务。现阶段定位是个人AI应用原型，业务背景与数据均为演示。

## 产品目标

直接用户是电商消费者。核心任务分为规则咨询、业务事实查询和申请操作。咨询规则不等于同意提交申请；订单号不等于身份凭据；申请成功不等于审核通过或款项到账。

第一版聚焦退货申请：表达意愿、选择订单、补充原因、核对规则、确认提交、查看申请状态。选择这条路径，是为了用一个可控任务覆盖多轮信息、知识依据、工具权限和执行验收。

“这个问题在真实业务中是否高频、是否足以显著减少人工耗时”仍需要真实调研，不能从原型功能直接推导。

## 与参考项目流程的关系

参考Adaptive-RAG的按意图分流、检索回答、订单工具、确认和核验思路，重新实现独立代码与界面。重点变化包括：

| 产品问题 | 本项目设计 | 可检查的结果 |
| --- | --- | --- |
| 用户只补订单号，原申请意图容易丢失 | 用结构化任务保留意图、订单、原因和阶段 | 补订单号后继续追问原因 |
| 有引用但难以核对规则 | 引用按钮直接打开完整演示政策 | 能看到版本、条件和例外 |
| “取消”可能只是隐藏确认卡 | 撤销当前待确认动作 | 原actionId再次确认不会执行 |
| 看回复无法确认操作真的完成 | 工具更新实际SQLite或浏览器演示记录 | 确认后订单状态或申请列表变化 |
| 模拟转人工容易被理解为已接通 | 保存演示工单与摘要，明确未接座席 | 可查看工单，不虚构客服已进入 |
| 技术路径命中被当作任务成功 | 用任务字段和后端结果验收 | 检查正确订单、确认与写入次数 |

本项目没有继承参考工程的Python后端、LangGraph、Embedding或向量数据库。检索是词面与业务标签融合；默认多角色工作流用规则执行，可选模型接入用于理解、依据生成和核验。

## 三个关键取舍

第一，把任务状态显式保存，避免完全依赖模型从长聊天记录中重建。这样容易定义必填字段、修改和确认失效规则；代价是需要维护任务类型与状态迁移，对新场景不能直接无限泛化。

第二，把理解与写操作分开。模型可以识别退货意图、生成政策解释；确定性工具负责归属、资格、时效、确认和幂等。额外确认增加一次交互，但能让用户核对实际影响。

第三，提供无需密钥的Pages演示，让面试官可以直接操作，同时保留Node服务端。演示易分享，但规则识别能力有限；真实模型需要服务端配置和单独效果验证，不能用规则回归替代模型评测。

## 如何验证

自动测试覆盖多轮续接、订单切换、跨会话确认、资格限制、重复提交、过期、订单版本变化、其他买家订单和模型降级。网页内12组模拟回归使用独立内存数据，不更改用户工作台。

退货正常任务的成功至少需要：意图保留；订单归属正确；原因收集完整；用户确认前没有写入；确认后恰好生成一条正确申请；状态和文案一致。仅出现“已提交”三个字不算通过。

当前案例是为已知功能设计的开发回归，不是冻结盲测。之后可以招募近似目标用户体验，收集自然表达，再建设未用于修改提示词和规则的独立验收会话。比较任务完成、重复输入、核验时间和错误操作，而非只比较答案流畅程度。

## 适合亲自参与的后续工作

1. 亲自跑通退货与取消任务，记录不自然的追问和未覆盖表达。
2. 为一个问题补充原始记录、需求与验收标准，再参与实现。
3. 整理30至50个来自实际体验或明确标为模拟的会话；保留独立验收部分。
4. 配置真实模型后，比较纯规则与模型辅助的表现、耗时和总调用量。
5. 找3至5位有售后经历的人做探索性任务测试，记录真实观察；样本性质和局限如实说明。

## 面试表述边界

这份实现由助手协助完成。你需要根据后续亲自理解、设计、修改和验证的内容说明贡献，不能把自动生成的全部代码说成自己独立从零开发，也不能声称已在真实企业上线。

完成实际参与后，可按证据表述：“我基于电商客服原型，围绕退货申请负责了某部分需求分析、任务状态与验收设计，借助开发工具完成迭代，并用某组任务验证了结果。”其中职责、数量和结果必须替换为真实记录。
